# СтройКонтроль — сопроводительная документация

## 1. Назначение

Система для руководителей строек и инженеров строительного контроля. По снимкам камер, установленных по периметру
площадки (кадр раз в 30 минут), она отвечает на вопросы:

- какие работы фактически идут и соответствует ли это графику;
- какой техники не хватает или какая простаивает;
- какие этапы отстают, какова готовность объекта и когда он будет закончен;
- что сделать, чтобы устранить отклонения.

## 2. Архитектура

```
Камеры (HTTP/RTSP) ─┐                   ┌─ SQLite: пользователи, стройки, объекты, план, камеры,
Эмулятор камеры ────┼─► Сервисный слой ─┤          снимки, детекции, вердикты, отклонения
Загрузка снимков ───┘   (FastAPI)       └─ Файлы: снимки, миниатюры, ленты эмулятора
                          │
                          ├─ Детектор: YOLO-World / YOLO / ONNX
                          ├─ Ядро: этап → вердикт → таймлайн → рекомендации
                          └─ Vue 3 SPA (nginx) ◄── браузер
```

Бизнес-логика (`app/core`) не зависит от веб-фреймворка и модели детекции. Её можно запускать и тестировать отдельно,
а детектор можно заменить без изменения правил.

## 3. Модель данных

Схема версионируется (`PRAGMA user_version`, `app/db.py`): новые колонки добавляются миграцией, старые базы
достраиваются при старте, а не ломаются. Текущая версия — 2 (история готовности в журнале вердиктов).

| Сущность | Ключевые поля | Назначение |
|---|---|---|
| users | email, name, password_hash (PBKDF2) | авторизация (HMAC-токены) |
| projects | owner_id, name, address, start_date, end_date | стройка |
| buildings | project_id, name, object_type, start_date, end_date | объект одного из 9 типов справочника |
| plan_tasks | building_id, code, parent_code, name, phase, is_summary, enabled, start_date, end_date | план: дерево работ справочника с этапом методики и сроками |
| cameras | project_id, building_id, name, zone, source_type (upload/http/rtsp/emulator), url, interval_min, active, emulator_cursor, emulator_clock, last_error | источники снимков; зона — часть площадки в обзоре |
| photos | building_id, camera_id, file_name, width, height, taken_at, detector, process_ms | снимок и время съёмки |
| detections | photo_id, cls, confidence, x1..y2 (доли кадра), activity (working/idle/unknown), idle_minutes, manual | найденная техника |
| verdicts | building_id, at, status, payload (JSON), completion_percent, planned_percent, idle_cost | снимок состояния и точка тренда |
| deviations | building_id, verdict_id, at, kind, severity, phase, message, equipment, photo_ids, zones | журнал отклонений |

Метаданные снимка, которые мы определили сами: время съёмки (`taken_at`), камера и зона. У входных фото метаданных нет,
поэтому время задаётся при загрузке (начало + интервал) или берётся из часов камеры либо эмулятора.

## 4. Алгоритмы

### 4.1. План работ

Справочник (xlsx, 377 позиций) разбирается с восстановлением номеров пунктов: Excel превратил их в даты.
Для выбранного типа объекта берутся отмеченные работы, и каждая привязывается к одному из 20 этапов методики
(правила по кодам и ключевым словам, первое совпадение). Сроки распределяются по типовым окнам этапов в долях срока
объекта; внутри этапа работы идут со сдвигом. Пользователь может отключать работы и задавать сроки вручную.

### 4.2. Детекция и активность

При приёме снимка срезаются однородные белые или чёрные поля (типичные для скриншотов камер) — до детекции, поэтому координаты рамок соответствуют сохранённому кадру. Детектор возвращает рамки 14 классов техники. Метки внешних датасетов и подсказки YOLO-World приводятся к классам
методики. Порог уверенности для анализа — 0.35.

Работает техника или стоит, определяется по соседним кадрам одной камеры. Если рамка того же класса совпадает с рамкой
на предыдущем кадре с IoU ≥ 0.92 (кадры не дальше 120 минут друг от друга), техника стоит; время простоя накапливается.
Простой дольше 60 минут даёт отклонение.

### 4.3. Определение этапа

Для каждого этапа считается балл:

`score = (0.6·покрытие обязательных групп + 0.3·объяснённость − 0.4·нетипичность) × вес наблюдаемости`

Объяснённость и нетипичность взвешены по IDF: редкая, специфичная техника (сваебойная установка) весит больше, чем
вездесущий грузовик. Этап подтверждён, если все обязательные группы присутствуют. Несколько подтверждённых этапов
разрешаются через график:
- плановые этапы выбираются первыми;
- внеплановый этап добавляется, только если есть техника, которую плановые этапы не объясняют;
- частично подтверждённый плановый этап «объясняет» свою технику, поэтому экскаватор на котловане без самосвалов
  читается как неполный котлован, а не как опережение по сетям.

### 4.4. Вердикт и отклонения

Окно анализа — 24 часа до выбранного момента. Типы отклонений:

| Код | Важность | Условие |
|---|---|---|
| NO_DATA | критично | нет снимков в окне |
| NO_ACTIVITY | критично | по плану идут наблюдаемые работы, техники нет |
| MISSING_EQUIPMENT | предупреждение | у планового этапа нет обязательной техники (с зоной и снимками) |
| BEHIND_SCHEDULE | критично (> 7 дн.) / предупреждение | этап не подтверждён дольше допустимой задержки старта |
| AHEAD_OF_SCHEDULE | информация | подтверждён этап, который по графику позже |
| NOT_IN_PLAN | предупреждение | подтверждён этап, отсутствующий в плане |
| UNEXPECTED_EQUIPMENT | предупреждение / информация | нетипичная или не относящаяся к плановым работам техника |
| IDLE_EQUIPMENT | предупреждение | простой техники дольше порога |
| CAMERA_SILENT | предупреждение | активная камера молчит дольше трёх интервалов |
| OUT_OF_VIEW | информация | плановые работы не наблюдаемы камерами (внутренние сети, отделка) |

### 4.5. Таймлайн и прогноз

Статусы этапа:
- «запланировано», «ожидает старта», «идёт по графику», «под угрозой», «отставание», «выполнено», «опережение»;
- «не наблюдается камерами» — статус по срокам;
- «не подтверждено» — этап вне обзора, но последующие этапы идут.

Пока с объекта не поступило ни одного снимка, система не показывает готовность, SPI и риск: вместо чисел
стоит «—», статус вердикта — «нет данных», а этапы получают статус «запланировано» или «не подтверждено».
Оценивать выполнение по срокам, выдавая это за факт, нельзя. То же при плане без активных работ.

Готовность — средневзвешенная по длительности этапов доля выполнения. SPI — отношение фактической готовности к плановой.
Прогноз окончания — плановая дата окончания плюс максимальное отставание этапа. Риск задержки:
- высокий — отставание больше 14 дней или SPI < 0.8;
- средний — есть отставание или SPI < 0.95;
- низкий — в остальных случаях.

SPI учитывается, когда по графику уже должно быть выполнено не меньше 5 %.

### 4.6. Рекомендации

Каждому типу отклонения соответствует конкретное действие: вызвать самосвалы под экскаватор, проверить причины простоя,
восстановить камеру и так далее. Отдельно отчёт содержит рекомендации по установке камер:
- обзорная камера на высоте 15–30 м;
- не меньше двух камер с противоположных углов;
- отдельная камера на въезде;
- без съёмки против солнца, с ИК-подсветкой для ночи и зимы;
- неизменное положение и зум камер;
- интервал съёмки 30 минут, для контроля простоя — 10–15 минут;
- разметка зон площадки.

## 4.7. Экономика отклонений

Минуты простоя и дни задержки — абстракция для руководителя, рубли — нет. Поэтому:

- **Простой измерим только по кадрам одной камеры.** Если снимки загружены без привязки к камере,
  система показывает не ноль, а прочерк с объяснением: считать простой не из чего.
- **Простой переводится в деньги.** Для каждой серии кадров, где техника стоит на месте, берётся максимум
  накопленного простоя (иначе один простой посчитался бы многократно) и умножается на часовую ставку
  из методики (`economics.shift_rates`, смена 8 часов). Ставки ориентировочные и заменяются договорными.
- **Дни отставания в рубли НЕ переводятся.** Умножение задержки графика на аренду всего парка даёт
  завышение в сотни раз (техника в эти дни не стоит под счётчик), а одна такая цифра разрушает доверие
  ко всем остальным. Вместо этого показывается справка: во сколько обходится день работы техники,
  фактически замеченной на объекте.
- **Динамика.** Каждый записанный в журнал вердикт сохраняет готовность, плановый процент и стоимость
  простоя, поэтому на объекте виден тренд, а не одна точка.

## 4.8. Безопасность

- Пароли хранятся как PBKDF2-хеши; минимум 8 символов, очевидные сочетания и только цифры отклоняются.
- Перебор пароля ограничен: 10 неудачных попыток на адрес за 15 минут дают 429.
- Ссылка на отчёт для заказчика — отдельный токен с областью действия «только этот отчёт» и сроком;
  как токен пользователя он не работает.
- Токены подписаны HMAC, ключ хранится в `DATA_DIR` и переживает перезапуск.
- Каждый запрос проверяет владельца: чужая стройка, объект, снимок и камера дают 404.
- Адрес камеры проверяется от SSRF: loopback, link-local (включая 169.254.169.254 — метаданные облака),
  multicast и служебные адреса запрещены при создании и повторно перед каждым опросом (защита от подмены DNS).
  Приватные сети 10/8, 172.16/12 и 192.168/16 разрешены намеренно: камеры на площадке стоят именно там.
  Для тестов и демостенда loopback открывается переменной `ALLOW_LOCAL_CAMERAS=1`.
- Имена файлов обезличиваются, путь собирается из идентификатора объекта: `../` в имени не выводит из каталога.
- Отчёт и изображения доступны по токену в query-параметре (иначе `<img>` не покажет снимок).
  Ссылку с токеном не следует пересылать наружу.

## 5. Условия и ограничения

- На вход только фото. Время съёмки задаётся системой, поэтому точность анализа зависит от корректности времени.
- Внутренние работы (инженерные системы, отделка) камерами не видны: статус определяется по срокам и помечается явно.
- Часть площадки может быть вне обзора. Этап без подтверждения при идущих следующих этапах получает статус
  «не подтверждено», а не «отставание».
- Без дообучения YOLO-World хорошо находит экскаваторы, краны и грузовики. Сваебойные установки, катки и
  бетононасосы распознаются хуже, для точности нужен `scripts/train_yolo.py` на датасетах хакатона.
  Ошибочные рамки можно удалить в интерфейсе — анализ пересчитается.
- Типовые окна этапов — экспертная оценка. Реальный календарный график заменяет их ручной правкой сроков.
- Отставание считается только с даты первого снимка: за период, когда камеры не снимали, задержка не вменяется.
- Ставки аренды в методике — ориентировочные (Москва, 2025); для договорных значений правится `data/methodology.json`.
- Качество детекции измеряется скриптом `scripts/eval_detector.py` (precision, recall, F1, подбор порога);
  порог 0.35 в методике — стартовое значение, его следует уточнить на своём датасете.
- Для дальних планов включается разрезание кадра на плитки: `DETECT_TILES=2` (медленнее вчетверо, но мелкая
  техника перестаёт теряться).
- Проверено на 400 снимках одного объекта: анализ 0,08 с, таймлайн 0,12 с, отчёт 0,14 с, галерея — два запроса на страницу.
- SQLite и один процесс достаточны для пилота. Для десятков камер детекцию стоит вынести в очередь.

## 6. Инструкция пользователя

1. Войдите или зарегистрируйтесь.
2. «Создать стройку»: укажите название, адрес и сроки.
3. «Добавить объект»: выберите тип и откройте шаг «План работ». Снимите галочки с работ, которых на объекте нет,
   поправьте сроки.
4. Шаг «Снимки и камеры». Время съёмки задаётся вручную: «одним моментом» — для разовой выгрузки
   за один обход площадки, «серия с интервалом» — для кадров, снятых подряд. Интервал спрашивается
   только во втором режиме. Без выбранной камеры простой техники и потери в рублях не считаются.
   Для демонстрации в реальном времени добавьте камеру «Эмулятор», загрузите в неё кадры,
   укажите время первого кадра и нажмите «Запустить»: каждые 10 секунд появляется кадр со временем +30 минут.
   Либо загрузите пакет снимков с началом и интервалом.
5. Нажмите на снимок: рамки техники, «стоит N мин», этап по снимку. Ошибочную рамку можно убрать.
6. Шаг «Этап и отклонения»: вердикт, фактический этап, что есть и чего нет по графику, отклонения со снимками,
   рекомендации. «Проанализировать и записать в журнал» сохраняет вердикт.
7. Шаг «Таймлайн»: цветные полосы этапов, точки подтверждений, линия момента анализа, готовность, SPI, прогноз.
8. Шаг «Отчёт»: HTML-отчёт по всей стройке (печать в PDF) и журнал отклонений.

## 7. API

Полная интерактивная спецификация — `/docs` (Swagger). Все роуты, кроме авторизации и справочников, требуют
`Authorization: Bearer <token>`. Для `<img>` и ссылки на отчёт допускается `?token=`.

| Метод | Путь | Назначение |
|---|---|---|
| POST | /api/auth/register, /api/auth/login | токен |
| GET | /api/object-types, /api/methodology, /api/catalog | справочники |
| GET/POST | /api/projects | стройки |
| GET/PATCH/DELETE | /api/projects/{id} | стройка |
| GET | /api/projects/{id}/overview | сводка по объектам |
| GET | /api/projects/{id}/report, /report.html | отчёт |
| GET/POST | /api/projects/{id}/buildings | объекты |
| GET | /api/buildings/{id}/plan | план |
| PATCH | /api/buildings/{id}/plan/tasks/{task_id} | работа: включение, сроки, этап |
| POST | /api/buildings/{id}/plan/bulk, /reschedule, /regenerate | массовые действия с планом |
| POST/GET | /api/buildings/{id}/photos | загрузка (multipart) и список с фильтрами `camera_id`, `cls`, `taken_from`, `taken_to` |
| GET | /api/photos/{id}, /api/photos/{id}/image?w= | снимок, изображение и миниатюра |
| PUT | /api/photos/{id}/detections | ручная правка рамок |
| POST | /api/photos/{id}/redetect | повторная детекция |
| GET/POST | /api/buildings/{id}/analysis?at= | вердикт (POST — с записью в журнал) |
| GET | /api/buildings/{id}/timeline?at=, /deviations | таймлайн, журнал |
| GET | /api/buildings/{id}/history | динамика готовности и потерь по записанным вердиктам |
| GET | /api/buildings/{id}/deviations.csv | журнал отклонений для Excel (UTF-8 с BOM, разделитель «;») |
| POST | /api/projects/{id}/report-link?ttl_hours= | ссылка на отчёт для заказчика (чтение, ограниченный срок) |
| GET | /api/public/report/{token} | отчёт по ссылке, без входа |
| GET/POST | /api/projects/{id}/cameras | камеры |
| PATCH/DELETE | /api/cameras/{id} | камера |
| POST | /api/cameras/{id}/poll, /frames, /reset | кадр сейчас, лента эмулятора, сброс |

Методика «этап → техника» целиком — в `docs/methodology.md`.
